# Database-Failure Recovery Actions

Council review: `2026-09-17-council-memo.md`. This plan incorporates it.

## Problem

`DatabaseFailureView` (`lib/src/database_failure_view.dart:6-56`) is a read-only
`ShadAlert`. Its copy tells the user to share "a data package if one is
available" (`:46`), but nothing in the app produces one, and the view offers no
actions at all — asserted by `test/database_failure_view_test.dart:33-47`.

The failure path at `lib/main.dart:374-378` runs after
`appDatabase.openForStartup()` fails and before any controller, storage
service, or `WebserverService` exists. The existing export surface is unusable
here:

- `DataManagementPage._exportFullBackup()` (`lib/src/settings/data_management_page.dart:282-293`)
  downloads from `http://localhost:8080/api/v1/data/export`, which needs both a
  running web server and an open database.
- The endpoint builds its zip from `BackupDataSources`
  (`lib/src/services/webserver/data_export/backup_data_sources.dart`), which is
  `PageCursor`s over live DAO queries.

A user whose database will not open has no way to save their data and no way to
escape the failure screen. This adds both.

## Decision

Two actions on the failure view, serialized against each other:

1. **Save recovery package** — a file the user can keep for later restoration.
2. **Reset local database** — destructive; removes local app data so the app
   can start clean.

Both build on archive build/save primitives extracted from
`DataManagementPage`, so the two call sites share one implementation.

No new dependencies. `archive`, `file_picker`, `share_plus`, and `path_provider`
are already in `pubspec.yaml`.

## Non-goals

- No automatic restore. The package is raw; a future restore flow can consume
  it. Nothing in this change reads it back.
- No logical (DAO-shaped) export, and no read-only SQLite dump. A database that
  failed to open cannot be read through DAOs. Revisit only with a real
  corruption sample.
- No change to the server export endpoint or `BackupDataSources`.
- `SharedPreferences` and the secure store are never touched. Credentials and
  settings survive a reset — `doc/AI_STORAGE_NOTES.md:52` requires that unless
  the user explicitly asks otherwise.

## Package contents

Built from `AppDirectories` (`lib/src/services/storage/app_directories.dart`)
directly. No database, no controllers.

| Entry | Source |
| --- | --- |
| `streamline_bridge.sqlite` | `AppDirectories.driftFile` |
| `streamline_bridge.sqlite-wal`, `-shm`, `-journal` | same path + suffix, when present |
| `store/...` | `AppDirectories.hive`, recursively |
| `log.txt`, `webview_console.log` | `AppDirectories.logs` + **explicit names** |
| `manifest.txt` | app version, platform, timestamp, entry list |

All three SQLite sidecars are collected because the journaling mode is not
pinned: `AppDatabase.defaults()` sets no `journal_mode`, so SQLite runs its
default rollback journal and an interrupted transaction leaves
`streamline_bridge.sqlite-journal` rather than `-wal`/`-shm`. Only one family
exists at a time, and each is existence-checked, so collecting all three costs
nothing. On a database-open or migration failure the journal can be exactly the
state needed to recover the file, so dropping it loses recovery.

**Log collection is an allowlist of the two known files, never a directory
walk.** On mobile `AppDirectories.logs` is the whole support/Documents root
(`app_directories.dart:14-27`, `doc/AI_STORAGE_NOTES.md:31`), so a recursive
walk would embed the database, the Hive store, plugins, and web-ui inside a
`logs/` prefix. A test pins this.

The name "recovery package" is deliberate: `SharedPreferences` and the secure
store are not in it, so "all data" would be a false claim
(`doc/AI_STORAGE_NOTES.md:45-52`).

## Shared module

New: `lib/src/services/export/archive_export.dart`

`zipFiles` and `saveArchiveBytes` are the moved `_zipFiles`
(`data_management_page.dart:39-45`) and the `FilePicker.saveFile(bytes:)` call
sites (`:429-433`, `:481-485`).

```dart
Uint8List zipFiles(Map<String, Uint8List> files);

Future<bool> saveArchiveBytes({
  required String fileName,
  required Uint8List bytes,
  String? dialogTitle,
});

enum DeliveryOutcome { saved, cancelled }

typedef ArchiveTarget = ({String outputPath, String finalPath});

Future<DeliveryOutcome> deliverArchive({
  required String fileName,
  required Future<void> Function(ArchiveTarget target) writeArchive,
  String? dialogTitle,
});
```

`deliverArchive` takes a writer callback rather than a built `File`, so the
caller decides where the archive is written while delivery owns everything
after it. Sequence:

- **Desktop.** Pick the destination with `FilePicker.saveFile(fileName:)`; `null`
  means cancelled. Stage in a `TempArchiveDir` the app owns, call
  `writeArchive(target)`, and only **after** the writer has returned (archive
  fully written and closed) copy the staged file onto the selected path. A
  failed pack therefore never touches the destination at all.
- **iOS/Android.** `writeArchive` into a `TempArchiveDir`, then `SharePlus`. A
  dismissed share sheet is `DeliveryOutcome.cancelled`. Cleanup uses the
  existing deferred grace timer, not immediate disposal — the OS share sheet
  reads the file asynchronously (`doc/AI_API_NOTES.md:367-370`,
  `DeferredFileCleanup` in `util/temp_archive_files.dart`).

`ArchiveTarget` carries both the physical output path and the logical final
destination, because the writer needs the final destination to detect a
destination that aliases one of its own sources while it writes somewhere else.

Staging is deliberately **not** beside the destination. The macOS build is
sandboxed and `com.apple.security.files.user-selected.read-write` grants the
selected URL rather than its directory, so a sibling staging file or directory is
denied on the signed build while passing on unsandboxed Linux
(`doc/AI_BUILD_NOTES.md` Footgun #6).

Picker behaviour, verified in `file_picker-11.0.2`: `saveBytesToFile` is a no-op
when `bytes == null` (`lib/src/file_picker_utils.dart:98`), and the macOS
(`file_picker_macos.dart:99-126`) and Windows (`file_picker_windows.dart:225-241`)
paths create nothing. The Linux path goes through the XDG portal save dialog
(`file_picker_linux.dart:144-191`), which **does** leave a zero-byte
placeholder; the copy overwrites it. Delivery also deletes a pre-existing
symlink at the destination before copying, so a link cannot be followed into a
source file.

`BackupTransferService.downloadExportZip` currently takes a `Directory` and
hardcodes `export.zip` (`lib/src/services/webserver/data_export/backup_transfer_service.dart:28-54`),
so `_exportFullBackup` cannot stream straight to the picked path yet. Add a
direct-destination-path variant taking a `File`, and have `_exportFullBackup`
use `deliverArchive`; keep the existing directory-based method until its other
callers are moved.

Call-site cleanup in `data_management_page.dart`: `_exportLogs` and
`_exportShots` call `zipFiles` + `saveArchiveBytes`; `_exportFullBackup` calls
`deliverArchive`; delete the local `_zipFiles`.

## StreamingZipWriter promotion

The packer uses the repo's own `StreamingZipWriter`, not `ZipFileEncoder`. The
project documents why it exists: "ZIP export keeps the custom streaming writer
because `archive`'s encoder buffers compressed entries"
(`doc/AI_API_NOTES.md:322-323`), and the bounded-memory invariant is "peak memory
scales with one page of records and one JSON record, never with backup size"
(`:319-320`). `ZipFileEncoder` holds each entry's compressed bytes in an
`OutputMemoryStream` (`archive-4.0.7/lib/src/codecs/zip_encoder.dart:246-257`),
which is exactly the large-SQLite case. Both council advisors flagged this
independently.

Move `lib/src/services/webserver/data_export/streaming_zip_writer.dart` to
`lib/src/services/export/streaming_zip_writer.dart` and:

- Let it target an arbitrary destination `File`, not only a temp `Directory`.
- Make `DataTransferLimits` optional so non-HTTP callers are not subject to the
  import-endpoint caps, while `data_export_handler.dart:102` keeps its existing
  limits and behaviour unchanged.
- Make the deflate level configurable; the packer uses best speed
  (`DeflateLevel.bestSpeed = 1`) since a large SQLite file is the bulk.
- Add a chunked `addFile(File, String entryName)` helper (bounded read buffer)
  so callers do not have to hand-roll the chunk loop.

`test/data_export/streaming_zip_test.dart` must still pass; extend it for the
new destination, limits, and level API.

Correction to an earlier draft of this plan: `archive`'s default is not
uniformly level 6. `ZipEncoder.encodeBytes`/`startEncode` default to
`bestSpeed`, but `ZipFileEncoder.create()` passes `level: level` explicitly, so
a `null` argument overrides that default and `add()` falls back to `?? 6`
(`zip_encoder.dart:128,249`). Moot here, since the promotion replaces the
encoder for this path.

## Packer

New: `lib/src/services/export/support_package.dart`

```dart
Future<File> buildSupportPackage({
  required String destinationPath,
  required SupportPackageSources sources,
});

Future<DeliveryOutcome> saveSupportPackage();
```

`SupportPackageSources` carries the already-resolved absolute paths (drift file,
hive dir, log dir, app version). **Resolve them on the main isolate before
spawning** — `AppDirectories` calls `path_provider`
(`app_directories.dart:14-20`), which needs the root isolate's platform channel.

The packing itself runs under `Isolate.run` so the synchronous deflate does not
block the frame loop. Only a `String` path crosses back out. Missing optional
files (`-wal`, `-shm`, `-journal`, either log file) are skipped, not fatal.

`saveSupportPackage` is `deliverArchive(..., writeArchive: buildSupportPackage)`
with the file name `decent-recovery-<timestamp>.zip`.

## Reset

New: `lib/src/services/storage/database_recovery.dart` — reset is a storage
concern, not an export concern.

```dart
class ResetReport {
  final List<String> moved;
  final List<String> renameFailures;
  final List<String> leftovers;
}

Future<ResetReport> resetDatabase();
```

Targets: `streamline_bridge.sqlite` (+ `-wal`, `-shm`, `-journal`) and, per owner decision
O1 below, the hive `store/` directory. Never `logs/`, `plugins/`, `web-ui/`,
`SharedPreferences`, or the secure store.

Mechanism is rename-then-delete:

1. Rename each target to a `<name>.reset-<timestamp>` sibling.
2. Delete the renamed path recursively.

This is a hazard reduction, not a guarantee. `openForStartup` attempts `close()`
but catches failure (`lib/src/services/database/database.dart:53-74`), so a
Windows handle may survive and block the rename. `ResetReport` therefore
separates `renameFailures` (target never moved; reset did not apply) from
`leftovers` (renamed but not deleted; out of the way, disk not reclaimed), and
the UI must never claim success on a partial result.

## Wiring

`DatabaseFailureView` gains two **required** callbacks and becomes stateful.

```dart
final Future<DeliveryOutcome> Function() onSavePackage;
final Future<ResetReport> Function() onResetDatabase;
```

Concrete functions are wired at the composition point, `main.dart:374-378`, per
the constructor-injection rule (`AGENTS.md:80-85`) — `main.dart` passes
`saveSupportPackage` and `resetDatabase`. Tests inject fakes and never touch a
platform channel or the filesystem. `DatabaseFailureApp` forwards them.

UI: two stacked full-width `ShadButton`s in the alert.

- **Save recovery package** — outline. Inline spinner while running, result line
  on success or failure.
- **Reset local database** — destructive. Opens a `ShadDialog` that restates
  exactly what will be removed and warns when no successful save happened this
  session, in which case the confirm button reads "Reset without a saved copy".

Reset is **not gated on a successful save** — a failed save (no disk space,
revoked permission) would otherwise strand the user. It **is** mutually
exclusive with saving: both buttons disable while either operation runs, and the
dialog is part of that exclusion, so a reset cannot race the packer. Both
advisor slots flagged the race.

The dialog must stay usable at 320 px width with 2x text
(`test/database_failure_view_test.dart:63`) — stacked buttons, scrollable body.

On success the screen shows "Data cleared. Close and reopen Decaid." No
auto-restart in this plan. No `ScaffoldMessenger` snackbars — the failure shell
is a standalone `ShadApp`.

## Slow path

Three avoidable costs were identified. Two are addressed; the first was
abandoned for a correctness reason recorded below.

1. **Double write — abandoned.** `_exportFullBackup` writes the zip to a temp
dir, then `File.copy`s it to the destination
(`data_management_page.dart:354-359`) — write, read, write. Streaming the
archive straight into the destination was implemented and then reverted: staging
runs in app-owned temp space and is copied onto the selected path, because the
macOS App Sandbox grants only the selected URL and denies sibling writes
(`doc/AI_BUILD_NOTES.md` Footgun #6). The desktop path therefore still pays the
copy. It is the same cost that shipped before this change, not a regression.
2. **Entry-sized memory.** `ZipFileEncoder` buffers one entry's compressed bytes
   before writing; a large SQLite file violates the project's bounded-memory
   invariant. The promoted `StreamingZipWriter` writes deflate chunks straight
   through.
3. **Blocking the frame loop.** The deflate is synchronous. Packing runs under
   `Isolate.run`, so the spinner animates.

Compression level is best speed for the package. Level choice has no correctness
effect; it is a size/CPU tradeoff and must be measured, not assumed.

## Review round

Independent review returned BLOCK with four blocking findings. All are fixed:

1. **A failed final rename destroyed the destination.** `writeArchiveToDestination`
   deleted the destination before renaming the partial, and the failure path
   then removed the partial too. It now renames an existing destination aside to
   a unique backup, renames the partial into place, restores the backup if that
   fails, and deletes the backup only after success.
2. **The promoted writer lost its structural ZIP32 guarantees.** Decoupling the
   HTTP caps also dropped the intrinsic 32-bit and 16-bit field bounds, so a
   permissive caller could truncate `uncompressedSize`, the entry count, or a
   name length into a corrupt-but-readable archive. Names, entry count,
   per-entry compressed and uncompressed sizes, offsets, and the effective
   archive ceiling (`min(configured, maxZip32)`) are now enforced independently
   of the optional HTTP limits, and compressed output is checked before every
   write.
3. **A destination inside the Hive tree could be read while being written.**
   `buildSupportPackage` opened the destination before enumerating Hive. Hive
   files are now enumerated before the writer is created.
4. **An explanatory comment violated `AGENTS.md:72`.** Removed.

Also fixed: the mobile path leaked its staging directory on success (it now
uses a deferred full `TempArchiveDir.dispose()`, as the previous implementation
did), and `manifest.txt` now lists itself.

## Review rounds

Six independent review rounds ran: five a-team rounds plus one external review on
PR #893. Each blocked on genuine defects, all are fixed, and every fix has a test
that was proven to fail without it.

The table records what each round found and what was done at the time. Rows 1-5
describe intermediate states of the delivery mechanism; **round 6 supersedes them
for anything to do with staging and renaming**, which no longer happen. Read the
row only for the defect it names, not as a description of the shipped code. The
current behaviour is in the sections above.

| Round | Blocking findings | Fix |
| --- | --- | --- |
| 1 | Failed final rename destroyed the destination; the promoted writer lost its ZIP32 structural bounds; a destination inside the Hive tree could be read while being written; an explanatory comment broke `AGENTS.md:72` | Backup-then-replace on Windows; structural ceilings enforced independently of the HTTP limits; Hive enumerated before the writer opens; comment removed. Also: deferred staging cleanup, and `manifest.txt` lists itself. |
| 2 | Backup/restore errors swallowed and backup naming not collision-free; the 16-byte data descriptor bypassed the archive ceiling; destination/source aliasing could truncate the database through `FileMode.write` | POSIX `rename` replaces atomically, so the backup dance is now Windows-only; descriptor checked before writing; aliasing rejected. |
| 3 | The guard compared the `.part` path, so the aliasing check never saw the selected destination | Callback contract now carries both paths (`ArchiveTarget`); `writeSupportPackage` extracted so the wiring is testable. |
| 4 | A symlinked parent directory bypassed the lexical guard; a pre-existing Hive file chosen as the destination was filtered from the archive and then overwritten | Per-file lexical identity was the wrong shape. Replaced with a canonical-directory rule using `resolveSymbolicLinks`. |
| 5 | Hive is enumerated recursively, so a destination in a nested subdirectory still aliased a source; a pre-existing `<destination>.part` symlink made `FileMode.write` truncate its target | Containment applied to the Hive directory; the predictable partial path was removed entirely in favour of a uniquely created staging directory beside the destination. |
| 6 (external PR review) | Staging beside the user-selected destination is denied by the macOS App Sandbox, which grants only the selected URL - and the full-backup path had been refactored onto the same mechanism; a retried partial reset reported `isClean` while `.reset-*` quarantine from the previous attempt was still on disk | Staging returned to the app temp directory followed by a copy onto the granted path, which also removes the Windows rename dance entirely; `DatabaseReset.run()` now reclaims pre-existing quarantine and reports it when deletion fails. |

Red proofs held for the sharpest fixes, including two from round 6: the
`.part`/destination wiring, the symlinked parent, the predictable partial path,
the sibling-staging location and the quarantine reclaim. Disabling each fix makes
its test fail; the partial-path one reproduces real truncation
(`Expected: 'SOURCE' / Actual: 'archive'`), and removing the quarantine reclaim
makes a retry report `isClean == true` while `.reset-*` data remains.

The round-6 sandbox finding reverted the single-write optimisation for the
desktop path: staging in the destination's directory was never compatible with
`com.apple.security.files.user-selected.read-write`. The remaining performance
wins (configurable deflate level, no per-entry buffering, packing off the frame
loop) are unaffected.

## Known residual gaps

Carried deliberately, none of them data loss:

- The desktop delivery path uses a copy, not a rename, so it is not atomic: an
  interrupted copy can leave a partial file at the user-selected path. This
  matches the behaviour that shipped before the extraction.
- The delete-failure reset path is covered by a POSIX-only test that relies on
  `chmod`. It would not hold if the suite ran as root.
- Delivery replaces a symlink at the destination but does not detect a
  **hard link** to a source file: `File.copy` would write through it and modify
  the linked source. Raised in review and accepted as follow-up hardening rather
  than a merge blocker, since it needs the user to have created a hard link into
  the app's own data directory. The fix is an identity check (inode/`stat`
  comparison against every source) or an exclusive-create-then-swap.
- No test drives >4 GiB entries, and the Windows path is untested on Windows.
- Hive is enumerated before the writer opens, so a file created inside the Hive
  directory during packing is not included. It also cannot be the destination,
  which the containment rule rejects.

Resolved from the council's advice: exclude `plugins/` and `web-ui/` from the
package; single destructive confirmation, no typed phrase; instruct manual
reopen rather than auto-restart; defer the read-only logical dump.
